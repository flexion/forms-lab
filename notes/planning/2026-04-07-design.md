# Final Project Design: LLM-Assisted Forms Platform

**Date:** 2026-04-07  
**Status:** Design Approved  
**Context:** LLM Class 2026 Winter Cohort Final Project  
**Timeline:** Two weeks (presentations April 20, 2026)  
**Repository:** New repo, referencing this class repo's Hono app as prior art

## Overview

A PDF-in, form-experience, PDF-out pipeline for government forms. Upload a government PDF form, the system ingests it into structured specs, delivers a filling experience (web form and/or conversational agent), and produces a completed PDF. LLMs are woven throughout where they add value, with systematic experimentation to demonstrate course material beyond basic API calls.

The catalog is the connective tissue—not just a component library but the system's self-documentation: architecture, design system, developer docs, user docs, specs, and project status. Because it's generated from code and structured data, it can't drift.

Git is the persistence layer for form definitions and assets. Branch-per-deployment CI/CD. GitHub for work tracking (issues/PRs), catalog for durable product artifacts (stories, architecture, decisions).

## Personas

Five personas span the full lifecycle: create → fill → operate → build → evaluate.

### Maya — Form Creator (Program Officer)

Works at a federal agency, needs to get paper forms online. Has PDF forms and policy documents but no technical skills. Cares about accuracy (digital form must collect exactly what paper form does), compliance (accessibility, plain language), and speed (can't wait months for IT).

**LLMs help Maya by:** Extracting specs from PDFs, suggesting form improvements, reviewing forms for quality, explaining complex conditions in plain language.

### Carlos — Form Filler (Citizen/Applicant)

Applying for a government benefit. May have limited English, low digital literacy, or accessibility needs. Needs clear language, guidance through complex conditional logic, and confidence he's filling things out correctly.

**LLMs help Carlos through:** Conversational filling (agent that explains questions and adapts flow), plain-language help text, contextual assistance.

### Priya — IT Operations (Agency Technical Staff)

Maintains infrastructure where forms are hosted. Needs reliable deployments, clear integration points with backend systems (submission routing, data export), and operational visibility. Doesn't author forms but needs to understand the system's architecture, configure deployments, and troubleshoot.

**The catalog serves as Priya's operational documentation.**

### Developer (Platform Engineer)

Building and maintaining the system. Needs the catalog to document architecture, conventions, component APIs, and design decisions. The catalog is the primary development reference.

### Evaluator (Instructor/Stakeholder)

Assessing the project's scope, technical depth, and polish. Needs to quickly understand what was built, what LLM techniques were applied, and how the pieces fit together.

**The catalog tells this story** — architecture overview, LLM integration points, design rationale, live demos.

**Catalog Integration:** Each persona gets a page in the catalog. User stories are written from their perspective and link back to them. Personas are living documents—as we learn more about needs, we update them.

## Data Model

Three core types with clear separation of concerns:

### DataCollectionSpec

The business domain model. **What data to collect:** fields, types, constraints, conditions, sensitivity, help text. Semantic, not presentational. Portable across delivery modes.

- Exists in class repo (`src/form_schema.py`)
- Reimplemented in TypeScript for new repo
- Stored as JSON in git
- Versioned by git commit SHA

### FormSpec

The UX/delivery layer. **How to present a DataCollectionSpec** as a form experience: page flow, section ordering, progressive disclosure, delivery mode per section (static form vs. conversational), layout hints, help text strategy.

- One DataCollectionSpec can have multiple FormSpecs
- References DataCollectionSpec by identity (not embedding)
- Stored as JSON in git alongside the DataCollectionSpec

### Submission

Validated, immutable data collected against a specific DataCollectionSpec version (identified by git SHA). Lives outside the spec repo. Links back to the exact spec state at collection time.

### Supporting Types

**FormProject** — a directory in git repo containing: DataCollectionSpec, one or more FormSpecs, associated assets (source PDF, policy docs, delivery config). The unit of collaboration.

**ChangeProposal** — a branch + semantic description of what changed. The universal unit of work for both humans and LLMs. Maps to a git branch / PR.

**Key Separation:**
- DataCollectionSpec = domain-stable (what data do we need?)
- FormSpec = UX-flexible (how do we ask for it?)
- Submission = immutable (what did we collect?)

## System Architecture

### Runtime: Hono on Bun

Single Hono application serving everything—forms platform, catalog, and API. Bun as the runtime. TypeScript throughout. Server-rendered JSX for pages, islands for interactivity where needed.

### Git as Persistence

Form projects (DataCollectionSpec, FormSpec, assets) stored as files in git repo. Adapter layer abstracts git operations—for demo, reads from local repo; adapter interface allows swapping in remote repo, GitHub API, or database later.

The semantic layer from prior brainstorming (spec-aware diffing, lifecycle states) is aspirational—implement only what user stories require.

### LLM Integration

Claude API (Opus 4.6/Sonnet 4.6 for MVP) behind protocol/interface abstractions. Each LLM capability is a discrete service: PDF extraction, FormSpec generation, spec refinement, conversational filling, help text generation, quality review.

**Strategy pattern with feature flags** — multiple implementations behind same interface, toggleable via catalog UI. Start with Opus/Sonnet, add experimental implementations (constrained sampling, finetuning, RAG) as follow-up work items.

### Deployment: Branch-per-Environment

Every branch gets its own deployment. Push a branch, CI builds and deploys to unique URL. Merge to main deploys to production. Enables following development on live branches and gives every PR a preview deployment.

**Infrastructure:** Simple server-per-branch approach—lightweight container or EC2 instance per branch, each running Bun + Hono, with form project repos cloned locally. Deploy is `git pull && restart`. Reverse proxy (Caddy/nginx) routes `branch-name.domain.com` to the right process.

**Rationale:** Simpler mental model than serverless, easier to debug, direct access to git repos on disk, supports future local model inference without rearchitecture.

### Authentication & Authorization

**The constraint:** Form authoring writes to git. Requires authentication (who are you?) and authorization (what can you do?).

**Auth boundaries:**
| Persona | Access | Operations |
|---|---|---|
| Carlos | Public (no auth) | Fill forms, submit, view published forms |
| Maya | Authenticated + authorized | Create forms, upload PDFs, refine specs, create proposals |
| Priya | Authenticated + authorized | Configure deployments, view status, manage projects |
| Developer | Authenticated + authorized | All operations + code changes |
| Evaluator | Public | Browse catalog, view forms, see architecture |

**Implementation: GitHub OAuth**

**Rationale:**
- Natural fit—git is persistence layer, GitHub hosts repo
- Authorization maps to GitHub repo permissions: write access = can author forms
- No user database to maintain—GitHub is identity provider
- Demonstrates real OAuth integration
- Appropriate scope for class project

**Architecture:** Auth middleware between routes and business logic. Routes that write to git require authenticated session with appropriate permissions.

## Comparison as a Protocol

**Core architectural pattern:** Any resource in the catalog can be compared between two git states. Foundational capability serving multiple use cases: reviewing changes, understanding evolution, debugging regressions, documenting decisions.

### Universal URL Pattern

```
/catalog/compare/<resource-path>?from=<ref>&to=<ref>

Examples:
/catalog/compare/projects/pardon-application/spec?from=main&to=add-military-service
/catalog/compare/architecture/conventions?from=v1.0&to=main
/catalog/compare/components/text-field?from=abc123&to=def456
```

### The Comparable Protocol

```typescript
interface Comparable<T> {
  load(ref: GitRef): Promise<T>
  compare(from: T, to: T): ComparisonResult
}

interface ComparisonResult {
  summary: string              // "3 fields added, 1 modified"
  changes: Change[]            // structured change list
  beforePreview?: ReactNode    // optional rendered before state
  afterPreview?: ReactNode     // optional rendered after state
}
```

### Resource-Specific Implementations

| Resource | Comparison Strategy | Preview |
|---|---|---|
| DataCollectionSpec | Semantic diff (fields, groups, conditions) | Rendered form (before/after) |
| FormSpec | Flow diff (pages, delivery modes, grouping) | Page flow diagram |
| Architecture docs | Text diff with markdown rendering | Side-by-side markdown |
| Components | Code diff + visual comparison | Rendered component states |
| Form submissions | Field-by-field value comparison | Highlighted differences |

### Semantic Diff for DataCollectionSpec/FormSpec

Highest-value comparison targets. Implementation scope: ~600-800 lines for core diff logic, tests, and UI. Becomes a user story.

**Example output:**
```
✓ Added group "Military Service History" after "Personal Information"
  ✓ Added field "served_in_military" (boolean)
    Required: true
  ✓ Added field "branch_of_service" (choice)
    Condition: Show when served_in_military = true
    Options: Army, Navy, Air Force, Marines, Coast Guard

✓ Modified field "conviction_date" in group "Offense Information"
  - Help: "Date of conviction"
  + Help: "Date of conviction (MM/DD/YYYY format)"
```

### Benefits

- **Shareable** — every comparison is a bookmarkable URL
- **Universal** — any resource, any two states
- **Type-appropriate** — each resource type provides domain-specific diffs
- **Composable** — project comparisons aggregate multiple resource comparisons
- **Extensible** — new resource types implement the protocol

**Architectural Decision:** "Why comparison is a protocol, not a feature." Rationale: multiple use cases, benefits from type-specific implementations, avoids one-size-fits-all diff logic.

## LLM Integration Points

Each LLM capability is a discrete service behind an interface. Serves specific personas and user stories:

### PDF → DataCollectionSpec Extraction (serves Maya)

Upload PDF form, LLM analyzes structure, fields, conditions, produces draft DataCollectionSpec. Highest-value integration—entry point for whole platform. Supporting policy documents can be ingested as additional context.

### FormSpec Generation (serves Maya)

LLM generates default FormSpec from DataCollectionSpec. Smart defaults: group related fields into pages, suggest delivery modes based on complexity, set up progressive disclosure for conditional sections.

### Spec Refinement / Authoring Assist (serves Maya)

Maya reviews specs in UI and says "make income section conditional on employment status" or "add section for dependents." LLM modifies spec via tool calls. Changes auditable—each edit is a commit.

### Form Quality Review (serves Maya, Priya)

LLM reviews spec for: accessibility issues, missing fields vs. source PDF, confusing flow, plain language compliance, consistency. Runs automatically on change proposals or on demand.

### Conversational Filling Agent (serves Carlos)

Agent conducts adaptive interview driven by FormSpec. Asks questions in natural order, skips irrelevant sections, explains jargon, flags sensitivity before collecting PII. Best for complex conditional logic that would overwhelm static form.

### Plain-Language Rewriting (serves Carlos)

Transform government jargon in field labels and help text. Can run at authoring time (precomputed, no runtime LLM cost) or on demand during filling.

### Policy Grounding (serves Maya)

Ingest supporting documents (regulations, policy memos), use them to generate better help text, validation rules, field explanations. RAG-based—LLM grounds suggestions in actual policy language with citations.

**Priority for MVP:** PDF extraction and FormSpec generation prove end-to-end pipeline. Conversational filling is second high-impact demo. Others layer in as subsequent stories.

## Experimentation & Evaluation Framework

**Core principle:** The project demonstrates systematic exploration of LLM techniques, not just API orchestration. Each LLM integration point supports multiple implementation strategies, toggleable via feature flags, comparable via metrics, demoable live.

### The Strategy Pattern

Every LLM capability defined by interface with multiple implementations:

```typescript
interface PDFExtractor {
  extract(pdf: Buffer, context?: PolicyContext): Promise<DataCollectionSpec>
  metadata: StrategyMetadata
}

interface StrategyMetadata {
  name: string
  status: 'baseline' | 'experimental' | 'production'
  courseTopics: string[]  // e.g., ["constrained-sampling", "finetuning"]
  evaluationResults?: EvaluationResults
}

// Implementations
class OpusPDFExtractor implements PDFExtractor { ... }
class ConstrainedSamplingExtractor implements PDFExtractor { ... }
class FinetunedExtractor implements PDFExtractor { ... }

// Factory with feature flag
function getPDFExtractor(): PDFExtractor {
  const strategy = getFeatureFlag('pdf_extraction_strategy')
  return PDFExtractorRegistry.get(strategy)
}
```

### LLM Integration Points with Multiple Strategies

| Integration Point | Baseline | Experimental Strategies | Course Topics |
|---|---|---|---|
| PDF Extraction | Opus/Sonnet API | Constrained sampling, Fine-tuned Qwen | Constrained sampling, Finetuning, Evaluation |
| FormSpec Generation | Opus/Sonnet API | Prompt-optimized, Rule-based heuristics | Prompt engineering |
| Policy Grounding | None (generic help text) | RAG (embeddings + retrieval) | RAG, Embeddings, VectorDB |
| Conversational Filling | Opus/Sonnet API | Fine-tuned Llama, Prompt-optimized | Finetuning, Prompt engineering |
| Help Text Rewriting | Opus/Sonnet API | Fine-tuned small model, Template-based | Finetuning |
| Quality Review | Opus/Sonnet API | Rule-based + LLM hybrid | Evaluation, Prompt engineering |

   - "Experiment: Fine-tune smaller model for PDF extraction"


### Evaluation Discipline

Each integration point defines success metrics:

| Integration Point | Primary Metrics | Secondary Metrics |
|---|---|---|
| PDF Extraction | Schema validity, field coverage | Latency, cost, local vs. API |
| FormSpec Generation | Usability (Maya's acceptance) | Time to first valid spec |
| Policy Grounding | Citation accuracy, policy alignment | User comprehension |
| Conversational Filling | Completion rate, data quality | Turns to completion, satisfaction |

Metrics guide decisions: "5x faster but 3% less accurate—worth it?"

## Vertical Slices

Each slice is a user story from persona's perspective, delivering complete capability. Leaves system demoable, polished, can be stopping point.

### Slice 0: Skeleton (infrastructure, not user story)

Hono app, catalog shell with personas, CI/CD with branch-per-deployment, git persistence adapter, data model types (DataCollectionSpec, FormSpec), basic routing, deployment to first environment.

Foundation that everything builds on.

### Slice 1: "Maya signs in to access form authoring"

GitHub OAuth integration, auth middleware, protected authoring routes, public vs. authenticated UI. Maya can sign in, system knows who she is and what she can do.

### Slice 2: "Maya uploads a PDF and reviews the extracted specs"

PDF upload → LLM extraction → DataCollectionSpec + default FormSpec. Both displayed in catalog as browsable, reviewable specs. Maya sees what system understood from PDF and how it proposes to present it.

**First LLM integration point.** Implementation uses Opus/Sonnet baseline. Establishes evaluation metrics.

### Slice 3: "Maya shapes the form experience"

FormSpec authoring UI—Maya reorders pages, adjusts grouping, picks delivery modes per section. LLM suggests: "personal info section is straightforward—static form works. Eligibility section has 12 conditional branches—conversational would handle better."

Maya works in proposal/draft mode. Live preview updates as she edits.

### Slice 4: "Maya reviews her proposed changes before publishing"

Comparison protocol implementation. Semantic diff for DataCollectionSpec/FormSpec. Maya sees: "Added page 'Military Service', reordered 'Offense Information' to page 4." Side-by-side rendered previews. Can compare proposal against published version. Links to GitHub PR for approval/merge.

### Slice 5: "Carlos fills out a published form"

Form renderer, form filling UI, submission capture. The FormSpec Maya shaped becomes working form. Carlos fills it out and submits. Submission captured and linked to spec version.

### Slice 6: "Maya receives a completed PDF"

Submission data mapped back onto original PDF template. Closes PDF-in/PDF-out loop. Maya can download filled PDF.

**At end of Slice 6:** Full PDF-in/PDF-out pipeline with LLM-assisted authoring is complete and demoable.

### Slice 7: "Maya refines the data model with LLM assistance"

DataCollectionSpec refinement—adding fields, changing conditions, modifying validation. LLM modifies spec via tool calls. Creates change proposal. Maya uses comparison UI from Slice 4 to review before merging.

### Slice 8: "Carlos completes complex sections through conversation"

Conversational filling agent for sections where FormSpec specifies that delivery mode. Same underlying spec, different experience. Demonstrates delivery spectrum.

### Subsequent Slices (as time allows)

- "Maya reviews form quality with LLM assistance" — accessibility check, completeness, plain language
- "Maya grounds help text in policy documents" — RAG-based policy ingestion
- "Priya views the deployment dashboard" — operational visibility in catalog

## Project Management Approach

**Catalog as durable record:** Personas, stories, architecture, decisions live in catalog. Always reflect current reality.

**GitHub as work tracker:** Issues and PRs are ephemeral work items. Issues reference story IDs (one-way link). Multiple PRs per story is fine—story tracks capability completion.

**Branch naming conventions:**
- `story/<story-id>` for user stories
- `experiment/<name>` for experiments
- Story ID format: `persona-short-description` (e.g., `maya-uploads-pdf`)

**Workflow:**

1. **Pick next story** from catalog
2. **Create branch** following naming convention
3. **Claude Code implements** — reads story acceptance criteria, reads architecture patterns, writes implementation plan, executes
4. **Review on deployed branch** — every branch gets unique URL
5. **Open PR** referencing story ID
6. **Review & merge** when satisfied
7. **Update story status** in catalog frontmatter (`status: completed`)

**Custom Claude Code skills** (build as needed, not speculatively):

- `/story` — given story from catalog, create branch, set up worktree, write implementation plan with full context
- `/catalog-update` — after implementing feature, update relevant catalog pages
- `/form-project` — scaffold new form project in git persistence layer
- `/experiment` — set up new experiment branch, strategy implementation template, evaluation harness

**The loop:** Catalog defines what to build → GitHub tracks work in flight → Claude Code executes → Catalog reflects result

**For two-week sprint with one implementor:** Overhead minimal. Pick next story, Claude Code implements as PR, review on deployed branch, merge when satisfied. Branch-per-deployment means always looking at real running code.
